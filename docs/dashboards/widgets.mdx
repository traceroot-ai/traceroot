title: Widgets
description: Build query charts, trace feeds, custom metrics, and time-series visualizations

**Widgets** are the fundamental visual building blocks of TraceRoot dashboards. Each widget represents an analytical query, a summary metric card, or a live stream of execution traces anchored to a dashboard.

TraceRoot provides two creatable widget types, rich filtering and aggregation capabilities, and flexible time-window controls.

## Widget types

When adding a widget to a dashboard, you specify its `type`:

| Type | Description | Content Specification |
| :--- | :--- | :--- |
| `query` | Computes metric aggregates and time-series distributions across spans or traces. | Full query specification (`view`, `filters`, `metric`, `breakdown`, `display`). |
| `trace_feed` | Displays a live, reverse-chronological list of execution traces matching search criteria. | Trace filter predicates and an optional row limit (`filters`, `limit`). |

## Query widget specification

A `query` widget executes an analytical aggregation across ClickHouse telemetry data. The `spec` object requires three fields — `view`, `metric` and `display`. `filters` defaults to `[]` and `breakdown` to `null`:

```typescript
interface QueryWidgetSpec {
  view: "spans" | "traces";
  filters?: WidgetFilter[]; // defaults to []
  metric: {
    measure: string;
    agg: "count" | "sum" | "avg" | "min" | "max" | "p50" | "p75" | "p90" | "p95" | "p99" | "uniq";
  };
  breakdown?: string | null; // defaults to null
  display: {
    type: "line" | "area" | "bar" | "pie" | "number" | "table" | "histogram";
  };
}
```

### View (`view`)

The underlying dataset to query:
- `"spans"`: Individual units of work (LLM calls, tool executions, chain steps, or vector searches).
- `"traces"`: End-to-end execution trees and top-level session requests.

### Filters (`filters`)

An array of filter predicates applied to the query. Each filter includes:
- `field` (string): The field to filter. On `spans` these are `name`, `span_kind`, `status`, `error_type`, `model_name`, `environment`, `is_root`, and `metadata`, plus the numeric measures below. Note that `is_root` and `metadata` are available via the API and alerts but do not appear in the builder UI.
- `op` (string): Operators are per field — string dimensions take `=`, `contains`, and `in` (with two exceptions: `is_root` accepts only `=`, and `metadata` accepts only `=` and `contains`), while numeric measures take `>`, `>=`, `<`, `<=`, and `=`.
- `value` (string, number, or array of strings): The value to compare against. The `in` operator takes a list of 1 to 100 non-empty strings (for example, `["LLM", "CHAIN"]`), while all other operators take a single string or number. Empty strings and non-finite numbers (`NaN`, `Infinity`) are rejected.
- `key` (string, optional): Required when querying keyed fields such as span attributes or custom trace metadata.

Example filter:
```json
{
  "field": "span_kind",
  "op": "=",
  "value": "LLM"
}
```

### Metric (`metric`)

Defines the quantitative measure and the aggregation function plotted on the y-axis:
- `measure` (string): The metric to aggregate. On `spans` these are `duration_ms`, `cost`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `total_tokens`, `tokens_per_second`, and `trace_id`, plus the `"count"` sentinel.
- `agg` (string): One of 11 aggregation functions — `count`, `sum`, `avg`, `min`, `max`, `p50`, `p75`, `p90`, `p95`, `p99` and `uniq`. The `pNN` functions are percentiles, so `p50` is the median, and `uniq` is an approximate distinct count (HyperLogLog).

<Warning>
  Each measure accepts only its own aggregations, not all 11. Numeric measures take `sum`, `avg`, `min`, `max`, `p50`, `p75`, `p90`, `p95`, `p99` and `uniq` — not `count`. The `count` sentinel takes only `count`, and `trace_id`, `user_id` and `session_id` take only `count` and `uniq`. So `{"measure": "cost", "agg": "count"}` parses but fails validation.
</Warning>

### Breakdown (`breakdown`)

An optional grouping dimension string (`string | null`, default `null`). When provided, the metric is segmented by this dimension (e.g. `"model_name"`, `"span_kind"`, or `"error_type"`). Not every field is groupable: `status` is a filter only, because it is effectively binary.

### Display (`display`) and breakdown rules

TraceRoot supports 7 display types. Depending on the visualization type, specific rules govern whether `breakdown` is required, optional, or forbidden:

| Display Type | Description | Breakdown Rule |
| :--- | :--- | :--- |
| `line` | Multi-point time-series line chart | **Optional**. Plots overall metric or separate lines per category. |
| `area` | Stacked or single-line time-series area chart | **Optional**. Highlights volume changes over time. |
| `bar` | Categorical bar chart | **Required**. Must provide a breakdown dimension to plot categories. |
| `pie` | Donut / pie distribution chart | **Required**. Must provide a breakdown dimension to calculate slices. |
| `number` | Single stat counter / KPI tile | **Rejected**. Must be `null`; renders exactly one headline number. |
| `table` | Tabular breakdown of values | **Optional**. Displays aggregated rows with optional groupings. |
| `histogram` | Value frequency distribution | **Rejected**. Must be `null`; compiles into automated value bins. |

## Trace feed widget specification

A `trace_feed` widget renders an embedded list of recent traces that match given filter conditions:

```typescript
interface TraceFeedSpec {
  filters: Predicate[];
  limit?: number; // Integer between 1 and 200 (defaults to 10)
}
```

- `filters`: An array of trace filter predicates (e.g. `[{ "field": "errors", "op": "gt", "value": 0 }]`). These use the trace-list predicate vocabulary — `eq`, `contains`, `in`, `gt`, `gte`, `lt`, `lte` — not the `=`/`>` operators a query widget's filters take.
- `limit`: Maximum number of traces to return. Must be an integer between `1` and `200` (`TRACE_FEED_LIMIT_MAX = 200`). If omitted, it defaults to `10` (`TRACE_FEED_DEFAULT_LIMIT = 10`).

## Display configuration (`displayConfig`)

In addition to `spec`, widgets accept an optional `displayConfig` object (`display_config` in API requests). This is a free-form JSON dictionary (`Record<string, unknown>`) used by frontend renderers to store layout options, custom color palettes, metric formatting, or axis thresholds.

```json
{
  "display_config": {
    "color_scheme": "emerald",
    "y_axis_label": "Latency (ms)",
    "threshold_warning": 2500
  }
}
```

## Time windows

When querying dashboard data or widget results, time windows are evaluated in one of three ways:

1. **Preset ranges**: Relative time windows anchored to the current moment. TraceRoot supports 10 preset identifiers:
   - `30m`: Last 30 minutes
   - `1h`: Last 1 hour
   - `3h`: Last 3 hours
   - `6h`: Last 6 hours
   - `1d`: Last 24 hours
   - `7d`: Last 7 days
   - `14d`: Last 14 days
   - `30d`: Last 30 days
   - `60d`: Last 60 days
   - `90d`: Last 90 days

2. **Explicit time ranges**: Absolute ISO 8601 timestamps passed via `start_time` and `end_time` (e.g., `start_time=2026-10-01T00:00:00Z&end_time=2026-10-02T00:00:00Z`). Both bounds must be provided together.

3. **Default window**: If neither a preset `range` nor explicit `start_time`/`end_time` parameters are specified, TraceRoot automatically defaults to the past **24 hours** (`1d`).

## Testing specs with `POST /widgets/query`

Before saving a widget to a dashboard, you can test its query specification statelessly using the `POST /api/v1/public/widgets/query` route.

This endpoint compiles and executes the `WidgetSpec` against your ClickHouse dataset without creating a persistent widget row in your database.

### Example: stateless query request

```bash
curl -X POST https://app.traceroot.ai/api/v1/public/widgets/query \
  -H "Authorization: Bearer $TRACEROOT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "range": "7d",
    "spec": {
      "view": "spans",
      "filters": [
        { "field": "span_kind", "op": "=", "value": "LLM" }
      ],
      "metric": { "measure": "cost", "agg": "sum" },
      "breakdown": "model_name",
      "display": { "type": "bar" }
    }
  }'
```

Response:
```json
{
  "columns": ["model_name", "cost"],
  "rows": [
    ["gpt-4o", 14.82],
    ["claude-3-5-sonnet-20241022", 8.45],
    ["gemini-1.5-pro", 3.12]
  ],
  "meta": {},
  "window": {
    "start_time": "2026-02-16T00:00:00Z",
    "end_time": "2026-02-23T00:00:00Z",
    "range": "7d",
    "clamped": false
  }
}
```

## Public widget API routes

The TraceRoot Public REST API provides six dedicated routes for widgets:

| Method | Endpoint | Description |
| :--- | :--- | :--- |
| `POST` | `/api/v1/public/widgets` | Create a new widget on a dashboard. (Strict creation: every call creates a new widget). |
| `POST` | `/api/v1/public/widgets/query` | Statelessly run a query specification over a time window without saving a widget. |
| `GET` | `/api/v1/public/widgets/{widget_id}` | Retrieve widget configuration, type, spec, and display settings. |
| `PATCH` | `/api/v1/public/widgets/{widget_id}` | Update a widget's title, spec, or display settings. |
| `DELETE` | `/api/v1/public/widgets/{widget_id}` | Hard-delete a widget from its dashboard. |
| `GET` | `/api/v1/public/widgets/{widget_id}/data` | Evaluate and return computed chart data for an existing widget over a time window. |

## Creating widgets

### Example 1: create a query widget (cURL)

The following example adds a P95 Latency line chart broken down by model name to an existing dashboard:

```bash
curl -X POST https://app.traceroot.ai/api/v1/public/widgets \
  -H "Authorization: Bearer $TRACEROOT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "9f2a7c14-3b8e-4d61-9a05-7e1c2f4b8d30",
    "dashboard_id": "cm2x9f7a40001l508h3k9d7bq",
    "title": "P95 Latency by Model",
    "type": "query",
    "spec": {
      "view": "spans",
      "filters": [
        { "field": "span_kind", "op": "=", "value": "LLM" }
      ],
      "metric": {
        "measure": "duration_ms",
        "agg": "p95"
      },
      "breakdown": "model_name",
      "display": {
        "type": "line"
      }
    },
    "display_config": {
      "y_axis_label": "Duration (ms)"
    }
  }'
```

### Example 2: create a trace feed widget (cURL)

The following example adds a filtered trace feed widget showing the latest error traces:

```bash
curl -X POST https://app.traceroot.ai/api/v1/public/widgets \
  -H "Authorization: Bearer $TRACEROOT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "9f2a7c14-3b8e-4d61-9a05-7e1c2f4b8d30",
    "dashboard_id": "cm2x9f7a40001l508h3k9d7bq",
    "title": "Recent Error Traces",
    "type": "trace_feed",
    "spec": {
      "filters": [
        { "field": "errors", "op": "gt", "value": 0 }
      ],
      "limit": 25
    }
  }'
```

### Example 3: create a widget using the TraceRoot CLI

You can also create widgets using the TraceRoot CLI by supplying a JSON specification file:

```json widget.json
{
  "project_id": "9f2a7c14-3b8e-4d61-9a05-7e1c2f4b8d30",
  "dashboard_id": "cm2x9f7a40001l508h3k9d7bq",
  "title": "Total Cost by Model",
  "type": "query",
  "spec": {
    "view": "spans",
    "filters": [
      { "field": "span_kind", "op": "=", "value": "LLM" }
    ],
    "metric": {
      "measure": "cost",
      "agg": "sum"
    },
    "breakdown": "model_name",
    "display": {
      "type": "pie"
    }
  }
}
```

```bash
traceroot widgets create --from-file widget.json
```

Or query widget data over a 7-day window directly from your terminal:

```bash
traceroot widgets data cm2x9g1b70003l508f2j6c4ra --range 7d
```
