To ensure system reliability and fair multi-tenant resource sharing, TraceRoot Cloud enforces rate limits across API endpoints.

<Note>
**Cloud-Only**: Rate limits apply strictly to **TraceRoot Cloud**. In [Self-Hosted](/developer/self-hosting) deployments (`ENABLE_BILLING=false`), rate limiting is disabled entirely, and throughput is limited only by your own infrastructure capacity.
</Note>

## Architecture and Keying

Rate limits are implemented using Redis storage shared across backend replicas, with an automatic in-memory fallback:

- **Workspace-Keyed**: Rate limits for API key traffic (such as telemetry ingestion and public reads) are keyed by your **workspace**, never by individual API keys. Generating additional API keys in the same project does not multiply your quota.
- **Member Sub-Buckets for User Sessions**: User-credentialed operations (such as interactive CLI sessions) include a per-member key (`...:{workspace}:{user}`). This prevents one member's terminal loops or scripts from consuming the read quota of their teammates.
- **Independent Buckets**: Different operations run in separate rate limit buckets, ensuring that bursts of write actions do not interfere with high-volume telemetry ingestion or read queries.

## Limits by Plan Tier

All rate limits are measured **per minute** and scale with your workspace subscription tier:

| Bucket | Free | Starter | Pro | Enterprise | Endpoints & Operations |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`ingest`** | 1,000 / min | 5,000 / min | 20,000 / min | 20,000 / min | Span and trace ingestion (`POST /api/v1/public/traces`) |
| **`read`** | 60 / min | 300 / min | 1,000 / min | 1,000 / min | Dashboard data reads, trace search, list/get endpoints |
| **`export`** | 30 / min | 100 / min | 1,000 / min | 1,000 / min | Full trace bundle export (`GET /api/v1/public/traces/{id}/export`) |
| **`sql`** | 20 / min | 60 / min | 120 / min | 120 / min | Direct ClickHouse SQL gateway queries |
| **`write`** | 60 / min | 60 / min* | 60 / min* | 60 / min* | Dashboard, widget, detector, and alert configuration writes |

<Note>
***Effective Global Write Limit**: While the architecture supports tier-based write scaling, all public write routes currently enforce a single effective global limit of **60 requests/minute** across all plans.
</Note>

### Why SQL and Export Have Dedicated Buckets

- **`sql`**: SQL queries execute directly against analytical ClickHouse tables and can scan extensive historical ranges. The bucket is throttled tighter than standard REST reads to keep interactive queries fast for all users.
- **`export`**: The trace export route constructs and serializes comprehensive multi-span trace bundles. Because bundle construction is computationally heavier than metadata lookups, exports ride a dedicated budget that scales independently from standard reads.

## Rate Limit Headers and HTTP 429 Responses

When a client exceeds its per-minute rate limit, TraceRoot responds with HTTP **429 Too Many Requests**:

```json
{
  "error": "too_many_requests",
  "detail": "Rate limit exceeded. Slow down and retry after the cooldown.",
  "retry_after": 60
}
```

The response includes standard rate limit headers:

| Header | Description |
| :--- | :--- |
| `Retry-After` | The number of seconds the client must wait before making another request. |
| `X-RateLimit-Limit` | The total request quota allowed in the current one-minute window. |
| `X-RateLimit-Remaining` | The number of requests remaining in the current window. |
| `X-RateLimit-Reset` | Unix epoch timestamp indicating when the quota window resets. |

TraceRoot Python and TypeScript SDKs, as well as OpenTelemetry OTLP exporters, automatically recognize `Retry-After` and back off requests exponentially.

---

## Best Practices

- **Batch Ingestion**: When using SDKs or OTLP collectors, batch spans before sending them to maximize throughput under the `ingest` budget.
- **Use Webhooks & Alerts for Monitoring**: Rather than polling read endpoints in rapid loops, configure [Threshold Alerts](/detectors/notifications) or use the in-app AI assistant.
- **Implement Jittered Backoff**: If writing custom automation scripts or CI pipelines, implement exponential backoff with jitter whenever handling 429 status codes.
