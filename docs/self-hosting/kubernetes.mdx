For scalable production deployments, TraceRoot provides an official Helm chart maintained at [traceroot-ai/traceroot-k8s](https://github.com/traceroot-ai/traceroot-k8s).

## Helm chart overview

The current stable release is **v1.1.1**.

### Key infrastructure model

- **ClickHouse**: **Deployed by default** via the Bitnami ClickHouse subchart the chart depends on (`clickhouse.deploy: true`). Set it to `false` and supply `clickhouse.host` to use an external cluster instead.
- **External Dependencies**: PostgreSQL, Redis, and S3-compatible object storage **must be provided externally** (e.g., AWS RDS PostgreSQL, AWS ElastiCache Redis, AWS S3, or in-cluster operators).
- **Credentials**: The chart never holds secret values. Every credential is read from a Kubernetes Secret you create, referenced by name through an `existingSecret` value.

To provision the AWS infrastructure as well as install this chart, use the [Terraform module](/self-hosting/terraform-aws) — it creates the Secrets, the load balancer and the TLS certificate for you.

## Installation steps

### 1. Add the Helm repository

```bash
helm repo add traceroot https://traceroot-ai.github.io/traceroot-k8s
helm repo update
```

### 2. Create the credentials Secret

The chart reads credentials from a Secret in the release namespace — named `traceroot` by default. Create it before installing:

```bash
kubectl create namespace traceroot --dry-run=client -o yaml | kubectl apply -f -

kubectl create secret generic traceroot \
  --namespace traceroot \
  --from-literal=database-url="postgresql://traceroot:<password>@postgres.internal.net:5432/traceroot" \
  --from-literal=redis-url="redis://redis.internal.net:6379/0" \
  --from-literal=clickhouse-password="$(openssl rand -hex 32)" \
  --from-literal=better-auth-secret="$(openssl rand -hex 32)" \
  --from-literal=internal-api-secret="$(openssl rand -hex 32)" \
  --from-literal=encryption-key="$(openssl rand -hex 32)" \
  --from-literal=clickhouse-ro-password="$(openssl rand -hex 32)"
```

That last key is needed only when `sqlGateway.enabled` is on, as it is in the values file below; leave it out if you keep the gateway off. It is the password for the account customer SQL runs as. The writer that owns the curated views has its own password generated by the provisioning hook and never stored, so there is no writer key to supply.

### 3. Prepare `values.yaml`

Create a `my-values.yaml` with your images, hostname and external endpoints. Every value below exists in the chart's [`values.yaml`](https://github.com/traceroot-ai/traceroot-k8s/blob/main/charts/traceroot/values.yaml), which lists the full set:

```yaml my-values.yaml
# Public URL of the app. The browser-facing API URL is derived by the chart.
betterAuth:
  url: "https://traceroot.example.com"

# Self-hosted: unlock every feature and skip the billing metering cron.
enableBilling: "false"

# Each service is imaged separately. Pin a git SHA; never deploy "latest".
web:
  image:
    repository: "<registry>/traceroot-web"
    tag: "sha-abc1234"
rest:
  image:
    repository: "<registry>/traceroot-rest"
    tag: "sha-abc1234"
# ...the same shape for worker, billing, detector, agent and both
# migrations.* images.

# Ingress takes a single hostname. The chart has no tls block: TLS is
# terminated by the ingress controller, which you configure through
# ingress.annotations.
ingress:
  enabled: true
  className: alb
  host: "traceroot.example.com"

# External PostgreSQL. The connection string itself lives in the Secret.
postgresql:
  existingSecret: "traceroot"
  secretKeys:
    databaseUrl: "database-url"

# External Redis.
redis:
  existingSecret: "traceroot"
  secretKeys:
    url: "redis-url"

# Object storage. The chart passes the bucket, region and endpoint but never
# credentials, so the pods need an identity of their own. On EKS, annotate the
# chart's service account with an IAM role that can reach the bucket.
serviceAccount:
  annotations:
    eks.amazonaws.com/role-arn: "arn:aws:iam::<account-id>:role/traceroot-s3"
s3:
  bucket: "my-traceroot-telemetry"
  region: "us-east-1"

# Bundled ClickHouse (Bitnami subchart).
clickhouse:
  deploy: true
  database: default
  auth:
    username: default
    existingSecret: "traceroot"
    existingSecretKey: "clickhouse-password"
  persistence:
    enabled: true
    size: 200Gi

# Optional: provision the identities the public SQL gateway runs as.
sqlGateway:
  enabled: true
```

On a cluster without IRSA, or against an S3-compatible backend that takes static keys, add `s3.endpoint` and pass the credentials as environment variables instead:

```yaml my-values.yaml
additionalEnv:
  - name: S3_ACCESS_KEY_ID
    valueFrom:
      secretKeyRef:
        name: traceroot
        key: s3-access-key-id
  - name: S3_SECRET_ACCESS_KEY
    valueFrom:
      secretKeyRef:
        name: traceroot
        key: s3-secret-access-key
```

### 4. Install the release

Deploy the Helm chart to your target namespace:

```bash
helm install traceroot traceroot/traceroot \
  --namespace traceroot \
  -f my-values.yaml
```

## Verifying pods and migrations

Once deployed, the Helm chart runs migration jobs before rolling out the application pods:

```bash
kubectl get pods -n traceroot
```

You should see:
- `traceroot-migrate-postgres-*` (Completed)
- `traceroot-migrate-clickhouse-*` (Completed)
- `traceroot-web-*` (Running)
- `traceroot-rest-*` (Running)
- `traceroot-worker-*` (Running)
- `traceroot-detector-*` (Running)
- `traceroot-agent-*` (Running)
- the ClickHouse pod from the subchart, when `clickhouse.deploy` is on

## Upgrades

To upgrade to a newer chart version:

```bash
helm repo update
helm upgrade traceroot traceroot/traceroot \
  --namespace traceroot \
  -f my-values.yaml
```
Database migration jobs will execute automatically prior to the application deployment rollout.
