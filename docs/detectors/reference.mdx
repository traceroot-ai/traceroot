Detectors continuously monitor production traces using an LLM-as-a-judge to catch failures, hallucinations, and behavioral regressions. This reference documents detector templates, trigger targeting conditions, model options, and finding structures.

## Templates

TraceRoot includes six built-in detector templates. Each template provides a pre-tuned prompt and a structured JSON output schema.

| Template | ID | What it checks | Output Schema |
|---|---|---|---|
| **Failure** | `failure` | Tool errors, timeouts, infinite loops, and swallowed errors | `category` (string) |
| **Hallucination** | `hallucination` | Claims in the final output not grounded in tool results | `type` (string), `hallucinated_claim` (string) |
| **Logic Error** | `logic` | Circular reasoning, contradictory actions, missed steps | `severity` (string), `error_description` (string) |
| **Task Completion** | `task` | Whether the agent answered the user's request | `success` (string), `what_was_missed` (string) |
| **Safety** | `safety` | PII exposure, prompt injection, harmful content | `risk_level` (string), `issue_type` (string) |
| **Blank** | `blank` | Custom prompt written from scratch | Custom |

### Failure (`failure`)

Evaluates traces for concrete operational and execution failures:
- Tool execution errors (non-zero exit status, exceptions in outputs)
- Silent failures (tools returning empty or null payloads when data was expected)
- Infinite loops (the same tool invoked 3 or more times with identical inputs)
- Timeouts or hung operations
- Swallowed error messages where the agent continued without recovery

**Output fields**:
- `category` (`string`): The classification of the failure (e.g., `"tool_error"`, `"timeout"`, `"infinite_loop"`).

### Hallucination (`hallucination`)

Evaluates whether the agent invented facts, figures, dates, or assertions:
1. Examines the agent's final output message or span.
2. Cross-references all tool call results present in the trace.
3. Flags the trace if specific claims cannot be verified from or contradict tool outputs.

**Output fields**:
- `type` (`string`): The nature of the hallucination (e.g., `"unsupported_claim"`, `"contradictory_statement"`).
- `hallucinated_claim` (`string`): The specific ungrounded claim extracted from the response.

### Logic Error (`logic`)

Evaluates logical coherence and execution integrity:
- Circular reasoning where the agent repeats steps without making progress
- Wrong conclusions where the final answer contradicts clear evidence in tool results
- Missed prerequisite steps
- Contradictory actions (e.g., creating a resource and immediately deleting it without reason)

**Output fields**:
- `severity` (`string`): The impact level (e.g., `"high"`, `"medium"`, `"low"`).
- `error_description` (`string`): Clear explanation of the flawed reasoning step.

### Task Completion (`task`)

Checks whether the agent accomplished the goal requested in the user's initial prompt.

<Warning>
  **Inverted `identified` logic**: For Task Completion, `identified=true` indicates that the task was **NOT** completed (failed or partially fulfilled). An agent that successfully completes the task yields `identified=false` and does not generate a finding.
</Warning>

**Output fields**:
- `success` (`string`): Explanation of whether and how the task succeeded or failed.
- `what_was_missed` (`string`): Specific deliverables, questions, or constraints the agent overlooked.

### Safety (`safety`)

Scans traces for security, compliance, and safety risks:
- **PII exposure**: Leaking sensitive personal data (SSNs, credit card numbers, addresses) from internal tool responses into user-facing outputs.
- **Prompt injection**: External content or user input attempting to hijack the agent's instructions.
- **Harmful content**: Toxic, discriminatory, or dangerous agent outputs.

**Output fields**:
- `risk_level` (`string`): Risk tier (e.g., `"critical"`, `"high"`, `"medium"`, `"low"`).
- `issue_type` (`string`): Categorization (e.g., `"pii"`, `"prompt_injection"`, `"harmful_content"`).

### Blank (`blank`)

Provides an empty prompt and output schema. Use this template to author custom criteria tailored to your specific application domain.

## Trigger Conditions & Targeting

Trigger conditions define which traces a detector evaluates. Traces must pass trigger filters and sampling before reaching the judge model.

### Targeting Rules

1. **60-Second Quiet Period**: Detectors evaluate a trace only after **60 seconds have elapsed with no new spans**. This quiet window ensures multi-step agents and streaming responses finish completely before evaluation starts.
2. **Evaluation Traces Are Excluded**: Traces generated by offline evaluations (`is_evaluation=true`) are **never targeted** by production detectors. This prevents evaluation runs from skewing production metrics and prevents recursive evaluation loops.
3. **AND Semantics**: All trigger conditions configured on a detector are combined using **AND** logic. A trace must satisfy every condition to be evaluated.
4. **Empty Conditions Match All Traces**: If a detector has no trigger conditions defined, all production traces are eligible for sampling.
5. **Any-Span Matching**: For multi-valued fields (`model_name`, `environment`, and `metadata`), the condition passes if **any span** in the trace contains a matching value.

### Trigger Fields

| Field | Label | Supported Operators | Value Type | Matching Semantics |
|---|---|---|---|---|
| `model_name` | Model | `=`, `!=` | String / Enum | Passes if any span in the trace called this model (`!=` means no span used it) |
| `environment` | Environment | `=`, `!=` | String / Enum | Passes if any span carries this environment tag |
| `cost` | Cost | `>`, `>=`, `<`, `<=`, `=` | Number (USD) | Total cumulative cost of the trace |
| `total_tokens` | Tokens | `>`, `>=`, `<`, `<=`, `=` | Integer | Total cumulative token count across all spans in the trace |
| `duration_ms` | Latency | `>`, `>=`, `<`, `<=`, `=` | Integer (ms) | Trace duration, from the earliest span start to the latest span end |
| `errors` | Errors | `>`, `>=`, `<`, `<=`, `=` | Integer | Count of error spans in the trace |
| `metadata` | Metadata | `=`, `contains` | Text (requires key) | Checks trace-level or span-level metadata for the specified key (`contains` is case-insensitive) |

## Judge Models

Detectors support both hosted system models and Bring Your Own Key (BYOK) providers.

### System Default Model

By default, detectors run on **`claude-haiku-4-5`** (`DETECTOR_SYSTEM_DEFAULT_MODEL_ID`). This model is chosen for its fast inference speed, low cost per token, and strong instruction-following capabilities for structured JSON output.

### TypeSafe AI (`jev-1.13.0`)

[TypeSafe AI](/ai-agent/byok) is a specialized BYOK provider that provides the **`jev-1.13.0`** decision model. Unlike general LLMs, TypeSafe AI is designed exclusively as a detector judge and is kept out of interactive chat and root cause analysis.

- **Decision Probabilities**: Rather than generating unstructured conversational text, Jev returns mathematical probability distributions across problem categories. The categories are the failure modes of the detector's template, not the template name — Hallucination offers `ungrounded_claim` and `contradicted_claim`, Logic Error offers `circular_reasoning`, `wrong_conclusion`, `missed_step` and `contradictory_actions`, plus an `other` catch-all. A blank or custom detector gets a single `problem` category.
- **The 0.5 Threshold**: A trace is flagged as a finding (`identified=true`) when the gate probability reaches or exceeds **`0.5`** (`gate >= 0.5`).
- **Standardized Summaries**: Jev summaries present the top identified category and runner-up with percentage probabilities and **no written rationale**:
  ```text
  Ungrounded claim (82% likely); runner-up: contradicted claim (12%); no written rationale.
  ```
  If no problem exceeds the threshold (`gate < 0.5`), the summary reports:
  ```text
  No problem found (18% chance of one).
  ```
  If the gate flags a problem but the specific category is ambiguous:
  ```text
  Problem found (76% likely), category unclear; no written rationale.
  ```
- **Decision Spans**: The judge's own execution trace records each System One call as a `DECISION` span, with the questions it asked and the probabilities it returned.

## Findings & the Runs Table

A detector's page lists its **runs**: every trace it evaluated. From the detector list, a detector's **Findings** count opens the same table filtered to the runs that identified a problem (`finding_id != null`).

### Runs Table Columns

| Column | Description | Click Action |
|---|---|---|
| **Timestamp** | When the detector evaluated the trace | — |
| **Judge Run ID** | Unique identifier for the evaluation run | Opens the judge's own execution trace, when the run was self-traced |
| **Trace ID** | ID of the evaluated production trace | Opens the trace in the TraceRoot trace viewer |
| **Signal ID** | The signal this run's finding joined | Opens the signal on the Signals page |
| **Agent Run ID** | The agent trace of the root cause analysis that ran on this trace | Opens the agent's analysis trace |
| **Identified** | Badge indicating whether a problem was flagged; a failed run reached no verdict and shows a dash | — |
| **Summary** | One-line summary produced by the judge model | — |
| **Status** | Status of the evaluation run (`completed`, `failed`) | — |

**Signal ID** reads **Not grouped** when grouping gave up on the finding, and a dash when the run identified nothing or has no signal yet. **Agent Run ID** is a dash when the run only joined a signal that was analysed on another trace; that signal holds the analysis.

### Finding Structure

When a detector flags a trace, it persists a finding containing:
- **Finding ID**: A unique identifier linking the detection result, the customer trace, and the RCA session.
- **Judge Summary**: A concise description of the failure mode.
- **Output Data**: A structured JSON object matching the template's schema (for example, `{ "category": "tool_error" }` or `{ "type": "unsupported_claim", "hallucinated_claim": "..." }`).

Findings are grouped into signals, and root cause analysis runs per signal rather than per finding. Opening a flagged trace from the detector pages opens the trace viewer with the agent's RCA session already loaded in the chat panel, so you can ask it follow-up questions; the agent's own analysis trace is a separate link, the run's **Agent Run ID**. See [Root Cause Analysis](/ai-agent/root-cause-analysis) for details on sandbox execution and automated fix pull requests.
